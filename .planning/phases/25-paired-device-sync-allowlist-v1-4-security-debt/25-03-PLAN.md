<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Human confirmation → trust | The "Codes match" tap is the trust decision; a rogue candidate shows a different code (and/or unexpected name) so the user declines. |
| UI mutation → transport allowlist | The transport only trusts what the store holds; UI add/remove must re-push `applyAllowlist` or the gate goes stale. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-25-02 | Tampering | pairing/unpairing ceremony | mitigate | Trust persisted only after mutual 6-digit code confirmation; unpair removes + re-pushes allowlist so future connects stop (SC-6). |
| T-25-03 | Information Disclosure | migration auto-adopt | mitigate | Launch detection shows a re-pair banner and NEVER seeds the allowlist from the connected peer (no auto-adopt) — empty allowlist keeps sync paused (SC-4). |
| T-25-07 | Repudiation/Spoofing | pairing-window abuse (rogue in-window) | mitigate | A rogue candidate computes a different code vs the real peer; two independent signals (code + friendlyName) shown; user declines. |
| T-25-06 | Spoofing | active installID spoof | accept | Residual MEDIUM, deferred; the code confirms intent, not secrecy, by design. |
</threat_model>
